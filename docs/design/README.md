# SimpleXray: веб-макет

`lab.html` — интерактивное демо для совместной проработки дизайна.
Android-приложение и VPN в нём не запускаются; реальные подписки не используются.

Четыре вкладки: Главная, Серверы, Подписки, Настройки. Роутинг пока вложен
в настройки; это предварительное предложение для обсуждения.

- Главная: выбранный сервер, подключение/отмена/отключение в демо-режиме,
  вымышленные текущие скорости и накопленные объёмы трафика, пинг и таймер.
  Круглая кнопка питания 112×112 px управляет подключением, повторным нажатием
  отменяет его или отключает; отдельной нижней кнопки нет. Кольцо пульсирует
  только при подключении, после подключения светится постоянно; reduced motion
  отключает пульсацию. Скорости и счётчики меняются примерно раз в секунду.
- Серверы: выбор, добавление и редактирование ручных серверов (название
  и JSON-конфигурация), удаление с подтверждением, имитация проверки доступности. У подписочных серверов
  доступен только просмотр конфигурации; запрет проверяется также при сохранении.
  Смена выбранного сервера или изменение его конфигурации отключает демо-сессию.
  Редактор проверяет JSON и наличие outbound-протоколов, но не валидирует
  полную схему Xray и не запускает конфигурацию.
  Начальный набор — 60 серверов (59 подписочных и один ручной). Есть поиск
  по имени/стране/подписке, сворачиваемые группы по подпискам или странам,
  сортировка по имени и числовому пингу. Непроверенные и недоступные идут
  после измеренных внутри группы. Поиск раскрывает найденные группы временно,
  при очистке восстанавливается состояние раскрытия. Для просмотра используется
  значок информации, для редактирования — карандаш.
  Цвет пинга: зелёный до 100 мс, жёлтый 100–250 мс включительно,
  красный свыше 250 мс, серый для недоступных и непроверенных.
  Массовая проверка показывает счётчик и итог доступных/офлайн; поиск очищается
  отдельной кнопкой. Название/счётчик серверов в подписке открывает список
  с отдельным фильтром по ID подписки, который можно сбросить.
- Подписки: добавление и изменение HTTP(S) URL, имитация обновления,
  удаление с подтверждением. Добавляются только вымышленные серверы.
  URL хранится в памяти страницы для повторного редактирования, не запрашивается,
  не выводится в карточке, не записывается в события холста или хранилище.
  Отмена формы не меняет подписку. Не вводите настоящие подписки и пароли.
- Название подписки: `Profile-Title` (обычный текст либо `base64:` UTF-8),
  затем `Content-Disposition` (`filename*`/`filename`), затем hostname URL
  без порта, пути и токена. Заголовки обрабатываются без учёта регистра;
  пустое/некорректное имя заменяется резервным вариантом. Формат заголовков:
  [HiddifyNG](https://github.com/hiddify/HiddifyNG/wiki#response-headers).
  В макете заголовки имитирует `subscriptionHeaders`: только
  `https://connect.example.com/subscription` возвращает имя «Основная подписка»;
  другие ссылки демонстрируют резервное имя по домену. Реальный HTTP не подключён.
- Лимиты: разбор `Subscription-Userinfo` (upload/download/total/expire), расход,
  остаток, прогресс и срок. Отсутствующие/некорректные значения не подменяются
  придуманными лимитами; total=0/expire=0 не показывают лимит/срок. Истёкшие
  подписки выделяются, превышение лимита не переполняет прогресс-бар.
  Начальная фикстура показывает 52 из 200 ГБ и 14 дней до истечения.
- Автообновление подписок находится в общих настройках и включено по умолчанию.
  Один часовой цикл обновляет все подписки независимо от времени добавления
  или ручного обновления отдельной подписки. При выключении автоматические
  обновления останавливаются, ручная кнопка остаётся доступной; повторное
  включение запускает новый часовой интервал. Уже начатое обновление завершается,
  параллельный запрос для занятой подписки не создаётся.
  Планировщик проверяет срок каждую минуту открытой страницы и при возвращении
  на неё; после пропущенных интервалов выполняется один общий цикл, не серия.
  Это имитация, не фоновая задача ОС. Переключатель и расписание не переживают
  перезагрузку страницы. Индивидуальные расписания удалены из редактора и карточек.
- Настройки: поиск, разделы подключения, DNS, роутинга, приложений, локальных
  входящих подключений, ядра, баз маршрутизации, JSON и диагностики.
  Тема и часовое обновление подписок остаются на главной странице настроек.
  «Журнал и отладка» показывает до 100 событий модели соединения и позволяет
  скопировать их. Это не настоящий журнал Xray-core. Тексты событий фиксированы:
  имена серверов, адреса, ссылки, ключи и конфигурации туда не попадают.
- Роутинг: редактируемые правила, обход LAN, вымышленные приложения и имитация
  обновления GeoIP/GeoSite. Подробности ниже.

## Настройки и тонкая конфигурация

Это новая модель интерфейса, не отражение ограничений текущего Android-кода.
Все сетевые поля формируют черновик профиля в памяти страницы. «Сохранить»
проверяет значения и фиксирует снимок; «Отменить» восстанавливает последний
сохранённый снимок, включая порядок правил. Переходы между экранами не теряют
правки. Настройки не переживают перезагрузку; работающий Xray не подключён.
Сохранение не перезапускает даже имитацию соединения. Тема и автообновление
подписок действуют сразу, вне сетевого черновика.

- Подключение: VPN/локальный прокси, IPv6, MTU, объявленные Android DNS,
  HTTP(S) цель и тайм-аут проверки. Режим без VPN отключает поля интерфейса
  и выбор приложений, сохраняя их значения.
- DNS Xray: основной и резервный резолвер (IP/UDP либо HTTPS/DoH), отдельные
  bootstrap IP для доменных имён резолверов, маршрут запросов, queryStrategy
  и кэш. DNS интерфейса и встроенный DNS ядра намеренно разделены; перехват
  Android DNS не реализован. Описание модели:
  [DNS Xray](https://xtls.github.io/en/config/dns.html).
- Роутинг: режим по правилам или всё через прокси; остаточный маршрут;
  Domain strategy; обход приватных IP. Правила можно добавлять, редактировать,
  выключать, переставлять стрелками и удалять с подтверждением. Условия:
  домен с поддоменами, точный домен, IP/CIDR, GeoSite/GeoIP; дополнительно сеть
  и диапазоны портов. Направления: proxy/direct/block. Сверху идут маршрут
  встроенного DNS и, при включении, обход LAN, затем пользовательские правила.
  В режиме global LAN и пользовательские правила не действуют, но сохраняются;
  явно выбранный маршрут DNS сохраняет приоритет.
- Для IPIfNonMatch не добавляется безусловное завершающее правило: оно бы
  помешало второму проходу с DNS. `client.defaultOutboundTag` задаёт выход,
  который будущий сборщик должен поставить первым в полном конфиге. Для прочих
  стратегий остаточный маршрут также представлен завершающим правилом.
  Порядок и семантика соответствуют
  [маршрутизации Xray](https://xtls.github.io/en/config/routing.html).
- Приложения: все / кроме выбранных / только выбранные, поиск; режим включения
  не сохраняется без выбранного приложения. Пакеты — фиксированные примеры,
  список установленных приложений из Android не читается.
- Входящие: SOCKS, UDP, опциональный HTTP, адрес и разные порты. Адрес вне
  loopback требует явного разрешения доступа из сети. Авторизации нет;
  предупреждение об этом остаётся видимым. Реальные сокеты не открываются.
- Ядро: Sniffing/routeOnly/HTTP-TLS-QUIC; Mux, concurrency, XUDP и UDP/443;
  Sockopt (domainStrategy, TCP Fast Open, keep-alive, user timeout, congestion);
  Policy уровня 0 (handshake, idle, half-close, buffer); уровень журналирования,
  access/DNS logs, маскирование IP и счётчики трафика. Параметры отключённых
  функций не попадают в активную часть профиля. Совместимость Mux, XTLS Vision
  и транспортов, а также доступность Sockopt зависят от выбранного ядра/ОС;
  они здесь не проверяются. Источники:
  [Mux/XUDP](https://xtls.github.io/en/config/outbound.html),
  [Sockopt](https://xtls.github.io/en/config/transports/sockopt.html),
  [Policy](https://xtls.github.io/en/config/policy.html),
  [логи](https://xtls.github.io/en/config/log.html).
- Базы: HTTPS источники GeoIP/GeoSite и прежняя имитация обновления. Файлы
  не загружаются, существование категорий не проверяется.
- Профиль: JSON-обёртка `client`, `core`, `outbound`, доступная для копирования.
  Это не исполняемый конфиг Xray: нет ключей, полных outbound и VPN plumbing.
  Будущий сборщик должен создать proxy/direct/block, учесть первый outbound,
  объединить дополнения outbound с выбранным сервером без потери транспорта.
  JSON-переопределения допускают только объекты log/dns/routing/policy/stats
  и полностью заменяют соответствующие секции, не выполняя глубокое слияние.
  Проверяются синтаксис, верхнеуровневая структура и отдельные типы, запрещены
  прототипные ключи. Это не полная валидация схемы и не `xray run -test`.
  Переопределения могут изменить смысл/приоритет правил, полей формы и логов.
  Данные профиля не отправляются в события холста или журнал диагностики.

## Добавление и состояния

- Основной ввод ручного сервера — ссылка VLESS, VMess или Trojan. Имя берётся
  из ссылки либо адреса; его можно изменить. JSON находится в «Расширенном вводе».
  Раскрытие/сворачивание секции не меняет сохранённый источник: ссылка обновляет
  предварительный JSON, а ручная правка JSON очищает ссылку и выбирает JSON.
- Поддержан ограниченный набор форматов: URI VLESS/VMess/Trojan, VMess Base64 JSON v2
  с aid=0, TCP/WS/gRPC, none/TLS, VLESS TCP Reality и Vision. IPv6 в URI — в скобках.
  Неизвестные параметры, повторяющиеся query-поля и неподдерживаемые сочетания
  отклоняются с предложением JSON, а не отбрасываются молча. Это не полный
  конвертер Xray и не проверка работоспособности ключа. Источники форматов:
  [XTLS](https://github.com/XTLS/Xray-core/discussions/716),
  [VMess v2rayN](https://github.com/2dust/v2rayN/wiki/Description-of-VMess-share-link).
- Кнопки вставки используют Clipboard API только по явному нажатию. При запрете
  доступа остаётся ручной ввод; запоздалый ответ не затирает новую правку или
  переоткрытую форму. Вставка на пустой главной определяет тип ссылки и открывает
  форму для проверки, без автоматического сохранения.
- QR использует локальные `BarcodeDetector` и `getUserMedia`, без библиотек с CDN
  или отправки кадра. Работает только при наличии поддержки QR в браузере и доступа
  к камере. Иначе показывается подсказка о ручной вставке. Камера останавливается
  после распознавания, закрытия, ухода со страницы или переключения вкладки браузера,
  включая случай запоздалого разрешения. Ограничения API:
  [BarcodeDetector](https://developer.mozilla.org/en-US/docs/Web/API/BarcodeDetector).
- Последний удалённый сервер открывает приветствие с добавлением подписки,
  вставкой и ручным вводом. Удаление выбранного сервера останавливает соединение
  и выбирает следующий, но не подключает его автоматически.
- Недоступный сервер приводит к состоянию ошибки с причиной, повтором и выбором
  другого сервера. В панели холста доступны «Первый запуск» и «Ошибка подключения».
  Пустой сценарий хранит свой временный набор отдельно от обычного; переключение
  не стирает изменения другого набора. Сценарий ошибки вызывает один тайм-аут при
  следующем подключении, чтобы можно было проверить успешный повтор.

Поля и переключатели сохраняют значения между вкладками, но не после
перезагрузки. Нет хранилища, запросов к подпискам или связи с Android/VPN.
Числовые поля и URL используют браузерную валидацию; это не полный валидатор
конфигурации Xray. По согласованию экран использует обычные продуктовые
тексты без меток «демо» и служебных пояснений. Это только визуальное
представление: подключение, проверки и обновления по-прежнему имитируются.

По умолчанию выбран Pixel 10 Pro: макет 412 × 919 CSS-пикселей примерно повторяет
пропорции физического экрана 1280 × 2856 из
[характеристик Google](https://store.google.com/product/pixel_10_pro_specs?hl=en-US).
Это выбранный масштаб макета, не утверждение о системной плотности Android/dp.
Также есть Redmi 10C: 360 × 825 CSS-пикселей, пропорции экрана 720 × 1650 из
[характеристик Xiaomi](https://www.mi.com/pk/product/redmi-10c/specs/).
На узком окне экран уменьшается пропорционально по ширине; на невысоком доступна
прокрутка холста. В рамке зарезервированы условные системные отступы 28 px сверху
и 24 px снизу; это не точная эмуляция панелей Android или выреза камеры.
Также доступны прежние три размера, светлый/тёмный фон, сетка и координатная метка.
Диалоги и затемнение ограничены дисплеем телефона; при изменении окна или
прокрутке страницы их положение пересчитывается. Длинные формы прокручиваются
внутри диалога, действия закреплены у нижнего края прокрутки.

Кнопка «Без рамки» открывает `?view=app`, сохраняя остальные параметры URL.
В этом режиме интерфейс занимает доступное окно без холста, с системными
safe-area отступами браузера. Вернуться к холсту можно кнопкой браузера «Назад».
Высота и границы диалогов учитывают
[VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport),
включая уменьшение видимой области при экранной клавиатуре. При масштабировании
жестом размер содержимого не уменьшается вслед за масштабом.
Поля ввода — 16 px, кнопки и кликабельные строки — не ниже 48 px; адаптация
карточек зависит от ширины экрана приложения, а не всего окна с холстом.
Проверены браузерные размеры 320–412 px, горизонтальное и короткое окно.
Физические телефоны и настоящая экранная клавиатура пока не проверялись.
Метка ставится кнопкой «Указать место» и кликом по экрану. Содержимое будущего
элемента обсуждается в чате. При перезагрузке состояние холста сбрасывается.

Для самостоятельного локального просмотра из корня репозитория:

```sh
python -m http.server 5173 --bind 127.0.0.1 --directory docs/design
```

Открыть `http://localhost:5173/lab.html`.

В совместной сессии используется Superpowers Visual Companion: HTML копируется
в каталог текущего экрана, а изменения и клики передаются через его сервер.
Файлы сессии, URL-ключ и события хранятся в игнорируемой `.superpowers/`.
Самостоятельный статический просмотр не отправляет координаты агенту.

## Проверка демо

Нужны Node.js 22+ с WebSocket и Chrome/Chromium. Запустить отдельный браузер
с временным профилем и CDP только на loopback (не использовать личный профиль):

```sh
google-chrome --headless --disable-gpu --no-first-run --no-default-browser-check --user-data-dir="$(mktemp -d /tmp/simplexray-design-test.XXXXXX)" --remote-debugging-port=9237 about:blank
```

На этом ПК бинарник находится в `/opt/google/chrome/chrome`.
В другом терминале выполнить из корня репозитория:

```sh
node --test docs/design/lab.test.mjs
```

Тесты управляют первой вкладкой этого тестового браузера. По умолчанию
открывают локальный `lab.html`; переменная `LAB_URL` позволяет проверить
страницу на локальном сервере. Проверяются переходы, демонстрационные
операции, формы, зависимости настроек, узкий экран, отсутствие ошибок JS
и внешних HTTP-запросов. После проверки завершить тестовый Chrome через Ctrl+C.
Тесты QR используют контролируемый результат детектора и видеопоток canvas для
проверки формы и освобождения камеры; физическая камера и распознавание настоящего
QR в автоматическом прогоне не проверяются.
